## 判定
1. **「云机 cmar 池漏空」在实例 146 不复现**：budget=32、free-list 有节点、sem 在
   增长——与**真机（budget=32/非空）一致**；run132-134 的「budget=0/池空」是**该
   实例特有**状态，非确定性云机行为；
2. 事件交付/消费同步（ADD≈GET），「内核事件滞留」在 146 也不成立；
3. 疑因：run132-134 读数来自**被重度探针**（含 run129 强制播种 SEGV + 多轮
   SIGSTOP/patch 注入）的实例 145；或 recipe 差异。146（v88，仅日志探针）健康。

## 结论与下一步
- 原「32 节点池 pop 失败/丢失」**无确定复现标的**——在复现前写修复=修幻影；
- 先做**可复现性判定**：干净启动（零干预）→ t=30/60/120/300s 采样 budget/freelist/
  sem + SF pid 稳定性；若始终健康 → 转向真 UI 显示阻塞的**真实**原因；
- 若复现 → 抓"首次从 32→0"的现场（时间序列 + 同期事件速率），再定修复。
