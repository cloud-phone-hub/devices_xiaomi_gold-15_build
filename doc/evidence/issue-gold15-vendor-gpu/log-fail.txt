- so+0x1F0470 位于 libGLES_mali.so 只读数据段（python seek 直读文件内容
  核实），被当「可写对象」解引用 → DDK 把只读静态模板当实例对象写。
- 相关字符串：`cmarp_backend_thread`、`Failed to close render list fd for
  CMAR signal flag (error %d)`、perfetto 数据源
  `cctx_memory_class_cmar_{hmem,prof_dump,signal,flush_chain,metadata_list}`、
  属性 `vendor.mali.cctx_memory_class_cmar_*` → CMAR = DDK 11.46 内存管理
  后台线程，事件条目由 DDK 自己的 GL 线程生产。

### 四、fd1 真身排除：非内核 TLSTREAM/PRFCNT fd，是 DDK 内部事件管道

- kbase r49p0：TLSTREAM_ACQUIRE = ioctl nr 18（0x40408012），成功返回
  anon fd「[mali_tlstream]」，受 timeline_is_permitted() 管控
  （mali_kbase_timeline_io.c:88，kbase_unprivileged_global_profiling 默认 0）；
  PRFCNT_SETUP = nr 57。
- DDK 反汇编全量提取 ioctl 号构造序列（movz w?, #0x80xx + movk w?,
  #0xTTTT, lsl #16 模式，43 处）：无 nr 18 / nr 57 → DDK 不打开内核
  timeline/perfcnt fd。
- 结论：backend 线程 poll 的 fd1 是 DDK 内部事件管道（字符串
  「render list fd」所指），生产者与消费者同在 DDK 进程内 → 崩因指向
  DDK 内部时序/初始化问题（只读静态模板未替换为可写实例、或受 guest
  timekeeping 错乱影响的超时 fallback），而非内核侧 fd 格式错配。
- 待运行时取证（下一 run）：恢复 adb 后抓 /proc/<sf>/fd + readlink 定
  fd1 具体指向（pipe/eventfd/memfd），为修复定层。

### 五、伴生问题登记：guest timekeeping 从 boot 起错乱

  173991s（QEMU 实跑 ~28min）；dmesg/logcat 秒数正常 → 从 boot 起即坏，
  非渐进漂移。
- 影响面：CMAR backend poll timeout、fence/watchdog 等所有时间敏感
  逻辑，可能是本卡点诱因之一。独立伴生问题，待查 QEMU virt 时钟源 /
