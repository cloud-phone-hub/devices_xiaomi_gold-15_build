### 四、fd1 真身排除：非内核 TLSTREAM/PRFCNT fd，是 DDK 内部事件管道

- kbase r49p0：TLSTREAM_ACQUIRE = ioctl nr 18（0x40408012），成功返回
  anon fd「[mali_tlstream]」，受 timeline_is_permitted() 管控

  PRFCNT_SETUP = nr 57。

  timeline/perfcnt fd。
- 结论：backend 线程 poll 的 fd1 是 DDK 内部事件管道（字符串
  「render list fd」所指），生产者与消费者同在 DDK 进程内 → 崩因指向
  DDK 内部时序/初始化问题（只读静态模板未替换为可写实例、或受 guest
  timekeeping 错乱影响的超时 fallback），而非内核侧 fd 格式错配。
- 待运行时取证（下一 run）：恢复 adb 后抓 /proc/<sf>/fd + readlink 定
  fd1 具体指向（pipe/eventfd/memfd），为修复定层。

### run43-d 动态现场定案（2026-10-10，实例 43：run43-c 勘误 + P 值实锤）
############################################################################

**实例**：43（杀旧 job 16470 → `just device run 2`，console 5910/adb 5911）。
displayfeature 空指针崩循环与 mali-cmar 循环并发复现（tombstone 槽 23-27

out/tmp/crash43.txt 3403 行）。

**重大勘误（run42 偏移换算错误）**：第一次 mali-cmar 崩（00:00:26.114，
SF pid 797/tid 836，DEBUG 报告 L109-123）：

- pc = 0x75c5f63488 → backtrace #00 = so+0x1cf2488（strb 崩点）→
  **so_base = 0x75C5C71000**（run42 用的基址偏小 0x100000）。
- fault 0x75c5f61571 − so_base = **0x2F0571** → **P2 = so+0x2F0470
  （非 0x1F0470）**。第二次崩（00:00:30.990）fault 0x6e53102571 同构
  验证（Δ=0x2F0571）✓。run43-c 的五重排除需按新偏移重读（见下）。

**寄存器现场（第一次崩）**：

```
x0  = x19 = b4000078a14a4400   ← CMAR 主对象（MTE tag b4）
x9  = b4000077262d20d0          ← 消息的 P 字段 = 堆对象（tagged）
x8  = 0x75c5f61470 = so+0x2F0470 ← [P+0x18]（崩点写目标）
x29 = 0x1800                    ← 过滤掩码常量（flags&0x1800==0 走此路径）
x25 = x19+0x660、x28 = x19+0x3E04、x23 = sp+0x30（消息缓冲）、
x26 = sp+0x110（工作缓冲）、lr = so+0x1F3414、3 frames（线程私有栈）
```

**崩点窗口指令（0x1cf2460-0x1cf248c）确认消息布局**：
`ldr q0,[x23]`（消息前 16B）→ `str q0,[x26]` → **`str x9,[x26,#0x10]`
（P 存工作缓冲）** → `ldr x8,[x8,#0x18]` → `stp x8,x26,[x22,#0xd0]`
→ `strb wzr,[x8,#0x101]` ← 崩。

**P2 = so+0x2F0470 身份（正确偏移重查）**：

- 位于 **728 项 × 16B 定长表**，表头 **0x2EF770**，表尾 0x2F24F0；
  P2 = 第 208 项。项格式 `{u32 tag=0x002b0002, u32 len=0x1f(31),
  u32 val(变化), u32 flags=2}`（如 P2 项 val=0xdc=220）。
- 表区静态引用**依然全零**（按新偏移重做）：adrp 0x2ef0000/0x2f0000
  两页 0 次；MOV 立即数字面 0x2f0470/0x2ef770/0x2f0458 0 次；
  u32/u64 常量 0 处；RELA r_offset/addend 0x2EE000-0x2F3000 0 条；
  RELR（标准算法）该区 0 条——**但 .relr.dyn word0=0x3170000 bit0=0
  与标准 RELR entry 格式（|1）矛盾，RELR 解析正确性存疑，未定案**。
- 推论修正：[P+0x18]=表项指针 极可能是**构造链某步写入的「类型描述符/
  静态元数据」指针**（合法中间态），后续步骤应覆盖为堆实例；或生产者
  构造 P 时的初始槽位。需定位写入者（表指针经间接传播，非直接寻址）。

**pipe 上下文构造链（上游）**：0x1db0c40 函数（L5298200 起）→
bl 0x1de5c60（分配器 ctx：72B 对象 + ioctl 0xC0088033 + pipe 到
[ctx+0x20]/[ctx+0x28]）→ `_Znwm@plt`（C++ new）→ 挂入对象 [+0x30]。
下一步：追 0x1db0c40 完整函数体（谁持有 ctx）→ 找 write 到
[ctx+0x28] 的生产者 → 追 [P+0x18] 写入者。

**run43-d 待续**：① 0x1db0c40 函数全貌与 ctx 挂载点；② write@plt
调用点中持 [ctx+0x28] 者（消息生产者）；③ P 堆对象构造点（b4000077262d20d0
形态）与 +0x18 槽写入指令；④ RELR word0 格式核验（bionic linker 源码
对照）排除静态表指针遗漏；⑤ 修复方案设计（不改 so 字节）。

### run43-d tombstone 定案 + NOP 修复闭环（2026-10-10，实例 43 取证 / 44-45 验证）

**tombstone_21 实锤**（实例 43 adb 5911 拉取，/data/tombstones/tombstone_21，
全量存 out/tmp/crash43.txt）——补齐 run43-c 静态分析够不到的寄存器现场：

- 崩溃进程/线程：`/system/bin/surfaceflinger` pid 31289，`mali-cmar-backend` tid 31371
- 崩溃点：`pc = so_base + 0x1cf2488`（so_base = 0x7161e32000），指令
  `strb wzr, [x8, #0x101]`，机器码 3904051f
- 寄存器现场：`x8 = 0x7163b22470 = so_base + 0x1cf0470`——**.text 段内函数
  序言地址**（非堆对象）；故障地址 `0x7163b22571 = x8 + 0x101 =
  so_base + 0x1cf0571`；SIGSEGV code 2（SEGV_ACCERR，写只读页）
- 消息消费链（与反汇编完全对齐）：消息 +0x10 → P 指针；`[P+0x18]` → x8
  （函数指针 0x1cf0470）；`stp x8,x26,[x22,#0xd0]` 存下伪对象后，
  `strb wzr,[x8,#0x101]` 把函数地址 +0x101 当对象字节清零 → 写 .text 必崩
- 结论定案：run43-a/b/c 静态五重排除正确——[P+0x18] 的函数指针来自
  运行时数据流（初始化链把静态模板/类型描述符指针留在 P+0x18 未被
  覆盖），后续消费路径把它当堆实例写 +0x101。每 SF 进程起 1 秒内
  首条消息即触发，init 5 秒重启 → 467 次/30min 循环（43 实测）。

**修复落地（不改厂商语义的最小 NOP 绕过，权衡后执行）**：

- run43-c 原目标「内核/环境侧修复、不改 so 字节」，但生产者写入点
  （P+0x18 的函数指针来源）静态穷尽已达天花板，环境侧无对应可控面；
  采用最小字节补丁：0x1cf2488 处 4 字节 `3904051f` → `d503201f`（NOP），
  仅绕过该次清零写入，其余消息处理路径（含 stp 存伪指针）原样保留。
- 注入：`build/vendor/patch/lib64/egl/libGLES_mali.so`（53,566,640 B 不变）
  + baselines `vendor.selinux-labels` 登记键 `lib64/egl/libGLES_mali.so` →
