# log-pass —— 判定实验原始输出（真机 root，2026-10-09）

> 说明：本 issue 是"定性/判定"类，尚未实施修复，故本文件不是"修复后通过日志"，
> 而是**判定实验的完整可复现命令与原始输出**（= 结论的证据）。
> 设备：Redmi Note 13 5G；`su` 可用（`uid=0(root) context=u:r:magisk:s0`）。

## 0. 可复现命令

```sh
D=fmvwkrheonugvgjb                       # 真机 adb 序列号
mkdir -p /tmp/soid && cd /tmp/soid

# 进程/uid
adb -s $D shell su -c id
adb -s $D shell 'su -c "pidof zygote64; pidof zygote; pidof dev.checker"'
adb -s $D shell "pm list packages -U | grep -i checker"
adb -s $D shell 'su -c "ps -Ao PID,PPID,USER,NAME | grep -E \"zygote|system_server|checker\""'

# 抓 maps（root）
adb -s $D shell 'su -c "cat /proc/1/maps"'        > init.maps
adb -s $D shell 'su -c "cat /proc/868/maps"'      > zygote64.maps
adb -s $D shell 'su -c "cat /proc/27625/maps"'    > app.maps
adb -s $D shell 'su -c "cat /proc/11089/maps"'    > settings.maps     # com.android.settings

# 抽 vendor .so 路径集合
for f in init zygote64 app settings; do
  awk '{print $6}' $f.maps | grep -E '^/(vendor|odm|vendor_dlkm)/' | grep '\.so$' | sort -u > $f.vendor.so
done

# 差集 / 交集
comm -13 zygote64.vendor.so app.vendor.so       # A \ Z
comm -23 zygote64.vendor.so app.vendor.so       # Z \ A
comm -12 zygote64.vendor.so app.vendor.so | wc -l
comm -13 zygote64.vendor.so settings.vendor.so  # settings \ Z
```

## 7b. 深挖：多进程对照（谁加载的）

进程祖先链（`ps -o PID,PPID,USER,NAME`）：

```
  PID  PPID USER         NAME
    1     0 root         init
  868     1 root         zygote64              ← zygote64 的父进程是 init
  870     1 root         zygote                ← 32 位 zygote，同为 init 的子进程
 1690     1 root         zn-nsdaemon-zygote_secondary
 1700     1 root         zn-nsdaemon-zygote
 1701     ? system       system_server         ← 亦为 zygote64 的 fork
 2292   868 webview_zygote
27625   868 u0_a299      dev.checker           ← 被测 App，父进程 = zygote64
```

各进程已加载 vendor `.so` 条数：

```
init      (1)     vendor_so =   0      ← 关键：init 一个都没有
zygote64  (868)   vendor_so =  56      ← zygote 自己 mmap
zygote 32 (870)   vendor_so =  56      ← 32 位 zygote 同样是 56
zn-nsdaemon-zygote*(1690/1700) vendor_so = 0
webview_zygote (2292) vendor_so = 56
system_server  (1701) vendor_so = 59
dev.checker    (27625) vendor_so = 59
```

- **非 init 继承**：`init` 的 1173 行 maps 里 vendor `.so` = **0**；`zygote64` 的 PPID=1，故它
  不可能从 init 继承到这批库——是 **zygote64 自己 mmap** 的。`grep libGLES_mali|libgpud|vulkan.mali|libc++`
  于 init maps 只命中 `/system/lib64/libc++.so`（另属 system 分区，非 vendor）。
- **32 位 zygote 同名集合完全一致**：

  ```
  仅64位zygote: 0   仅32位zygote: 0   同名: 56
  ```
  （32 位 zygote 的 56 条全在 `/vendor/lib/*.so`，basename 与 64 位逐条对应）
  ⇒ 这是 **zygote 启动时的 ABI 对称预加载**，不是被某个 App 的 GL 调用触发的。
- **webview_zygote 与 zygote64 完全相同**（`webview\z64 = 0`、`z64\webview = 0`）⇒ 纯继承。
- **system_server 与 App 同构**：`system_server \ zygote64 = 3`，且**就是同样那 3 条**
  （`arm.graphics-V5-ndk.so`、`hw/mapper.mediatek.so`、`libdrm.so`）⇒ 这 3 条不是
  "device-checker 的 GL 检查专属"，而是**进程运行时经 graphics 路径各自 dlopen**（App 与 system_server 都会）。

相关属性/实物（真机）：

```

ro.hardware.gralloc = (空)

```
